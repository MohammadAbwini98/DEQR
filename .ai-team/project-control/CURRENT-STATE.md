## Large-File / Maximum-Speed Program — Phase 00 (2026-08-20)

A separate, additive program runs alongside the open M1/M2 gates: remove the ~32 MB ceiling and maximise stable optical throughput. Its plan is phase-gated 00 through 12. **Phase 00 (baseline audit, limit discovery, measurement harness) is COMPLETE and PASSED.** Full report: `.ai-team/reports/performance/PHASE-00-AUDIT.md`.

- **The ~32 MB ceiling is a field width, not a size constant. DEMONSTRATED AT RUNTIME, not read off a constant.** The frame header carries `blockCount` as `uint16` (`src/core/protocol.ts:69`) against a sender block size fixed at 512 bytes (`src/main/session-manager.ts:14`), so v1's entire transport capacity is `512 x 65,535 = 33,553,920` bytes. A boundary probe walked it byte by byte: 33,553,818 source bytes serialize to exactly 33,553,920 and yield K=65,535; one byte more is rejected by the sender gate and the encoder throws `Invalid block count K=65536. Must be 1-65535.` A nominal 32 MiB file is 512 bytes past the ceiling and is refused before it is read. **Raising `MAX_FILE_SIZE` would change nothing.**
- **v1 cannot be widened from inside.** `segmentNumber` exists as `uint16` but the encoder always writes 0 (`src/core/fountain-encoder.ts:88`) and the receiver rejects any other value (`mobile-web/src/protocol.ts:39`). The next walls after the block count are `MAX_FILE_SIZE` / `LIMITS.maxFileBytes` at 64 MiB, then `totalPayloadLength` as `uint32` at 4 GiB-1.
- **Extension-dependent transfer speed: DISPROVED as a transport effect.** Identical bytes under `.txt/.pdf/.zip/.xlsx/.bin`, five samples, running order rotated per sample: identical block counts throughout; with filenames held to equal byte length, exactly one distinct container digest excluding the filename field and one container length. Per-extension means fell within 0.8% and 2.6% against 21% run-to-run noise, and in 7 of 10 samples the slowest cell was whichever extension happened to run first. No transport, framing, FPS, compression, or QR setting reads the extension anywhere; the only extension logic in the codebase is the blocked-list refusal, which is categorical rather than slow. The only way a *name* changes a transfer is its **length**, which moves the container by that many bytes and the block count by at most one.
- **The real content effect is entropy, and DEQR captures none of it.** `compressIfBeneficial` (`src/core/compression.ts:11`) is never called by the sender — `src/main/session-manager.ts:82-83` hard-codes `compressed: false` — so a corpus gzip shrinks to 12.8% still ships at full size and takes ~7.8x longer than it needs to. Users who name compressible things `.txt` and incompressible things `.zip` see exactly the correlation they report, from a mechanism unrelated to the extension.
- **Software is not the bottleneck anywhere.** The optical link is 10 FPS x 512 B = 5,120 B/s. Measured stage rates: container serialize 2,450-5,088 MiB/s, file read 556-2,376 MiB/s, SHA-256 372-465 MiB/s, PWA verify 172-299 MiB/s, fountain encode 52-212 MiB/s, fountain decode 44-61 MiB/s — the slowest is ~9,000x the link. A full systematic pass at the v1 ceiling takes **1 h 49 min** with zero loss and no repair frames.
- **The receiver has no persistence at all.** No OPFS, no IndexedDB, no incremental write anywhere in `mobile-web/` — verified by search, not assumed. Its decoder holds 1.25-1.74x the payload with 129-380 bytes of object overhead per 512-byte block, then makes 2-3 further whole-payload copies to reconstruct, parse, verify, and export.
- **Recorded for later phases, not acted on:** the frame header checksum is one XOR byte over 19 bytes (~1/256 chance of accepting a corrupted header) and **payload bytes carry no checksum at all**; verification is all-or-nothing at the end over a fully materialised buffer; the UI capacity copy in `src/renderer/App.tsx:240` and `src/renderer/components/Dashboard.tsx:19` states the wrong number.
- **Harness:** `scripts/bench/phase00-baseline.ts` (boundary/capacity/extension) and `scripts/bench/phase00-receiver-memory.ts`, both offline and payload-safe, both reusable by later phases with a different `--label`. Evidence lands in `.local-run/bench/`, which is gitignored, so the report is the durable copy.
- **Stated deviation:** the in-app development-only telemetry stream the plan asks for was deliberately **not** built. Most of its counters already exist in shipping code, the rest are measured by the harness, and the three that need in-app wiring attach to subsystems Phases 04/05/06 replace. Reasoning is recorded in section 9 of the report.
- **No shipping code changed.** Desktop **286 PASS / 25 files** and PWA **63 PASS / 11 files** are unchanged from the pre-phase baseline, which is the expected outcome. Both typechecks, doctor (0 warnings) and drift all PASS.
- **Phase 01 (Protocol v2) is unblocked** and must carry forward: a segment-relative frame header with a real segment number, 64-bit-safe total-size semantics, a payload checksum stronger than one XOR byte, and a block size that is a transport profile rather than a constant.

## Large-File / Maximum-Speed Program — Phase 01 (2026-08-20)

**Phase 01 (DEQR v2 binary protocol) is COMPLETE and PASSED.** Normative spec: `.ai-team/engineering/PROTOCOL-V2.md`. Gate record: `.ai-team/reports/performance/PHASE-01-PROTOCOL-V2-REPORT.md`.

- **v2 is defined and implemented, and is NOT wired into anything.** The sender still emits v1 and the receiver still reads v1. No v1 file was modified: `src/core/protocol.ts`, `src/core/container.ts`, `src/core/fountain-*.ts`, `mobile-web/src/protocol.ts`, and `protocol/test-vectors/` are byte-identical to before the phase, so the C# parity suite and every v1 claim stand untouched.
- **The 32 MB field width is gone by construction.** A one-time session manifest carries filename, SHA-256, sizes, segmentation, compression mode and FEC profile; compact data frames carry `sessionId`, `fileId`, `segmentIndex`, `symbolId`, `sourceSymbolCount`, payload and a CRC-32 in 32 bytes of overhead. `segmentIndex` is a live u32 rather than v1's constant zero, so segments are real and each is independently decodable.
- **64-bit means `bigint`, not "a big number".** Sizes and every derived offset are `bigint` end to end; the only route to `number` is `toSafeNumber`, which throws `PRECISION_LOSS` above `Number.MAX_SAFE_INTEGER` rather than rounding. Proven, not asserted: `2^63 + 12345` round-trips exactly, and a segment offset of `2^26 x 3,999,999,999` is computed exactly above the safe-integer boundary. A 5 GiB transfer is fully described by a **126-byte** manifest with nothing of that size allocated.
- **Decoder state is bounded by a segment, never by the file.** Asserted directly: a 5 MiB and a 5 TiB transfer at the same segment size have byte-identical per-segment working sets and differ only in segment count. This is the property Phases 03, 06 and 07 all build on.
- **Integrity is layered and the layers do not substitute for each other.** CRC-32/ISO-HDLC over the whole frame (header *and* payload) replaces v1's single XOR byte over 19 header bytes with no payload check at all; structural validation binds a frame to its manifest; SHA-256 over the reconstructed original file remains the sole authority on identity.
- **The parser never throws.** Every malformed input is a typed `DeqrV2Error`. About 20,000 fuzz inputs - random buffers, prefix-forced buffers, every single-byte mutation of a valid frame and manifest, every truncation, every declared-length boundary - produced zero escaped throws. **v1 frames are reported as `V1_FRAME`, never as corruption**, so a version mismatch cannot present to a user as a camera or lighting fault.
- **One codec, not two.** v1 forced the PWA to carry a second implementation of the wire format because `src/core/protocol.ts` is written in terms of Node `Buffer`. v2 is `Buffer`-free, so the Electron sender and the iOS PWA import the same module. Verified through the **production** Rollup path the receiver builds with, not just vitest: a 20,691-byte ES module with **zero Node imports and zero `Buffer` references**.
- **21 golden vectors** in `protocol/test-vectors-v2/` (9 valid, 12 rejection cases), regenerated byte-identically by `npm run vectors:v2:generate`. CI now regenerates and runs `git diff --exit-code` on them, the same guarantee the v1 vectors already carry.
- **Stated deviations:** data frames deliberately omit the logical file offset (derived from the manifest instead - eight bytes per symbol against a 5,120 B/s link, and the plan's own no-repeat rule), and the spec lives under `.ai-team/engineering/` rather than the repository root because `AGENTS.md` names that as canonical.
- **Suite counts after the phase:** desktop **395 PASS / 28 files** (up from 286 / 25), PWA **71 PASS / 12 files** (up from 63 / 11). Both typechecks, both production builds, `test:packaged`, doctor (0 warnings) and drift all PASS.
- **Open protocol values, deliberately unchosen:** `segmentSizeBytes` (field accepts 64 KiB-64 MiB; plan's benchmark range 1/2/4 MiB) and `symbolSizeBytes` (field accepts 32-4,096 B; v1 shipped 512). Phase 04 fixes both from measured verified-payload throughput, not from these bounds.
- **Phase 02 (desktop streaming sender) is unblocked.**

## Large-File / Maximum-Speed Program — Phase 02 (2026-08-20)

**Phase 02 (desktop streaming sender) is COMPLETE and PASSED.** Gate record: `.ai-team/reports/performance/PHASE-02-DESKTOP-STREAMING-REPORT.md`.

- **v1 holds two times the file resident before it draws a frame; v2 holds 1.05 MiB regardless of the file.** Measured on both paths over identical corpora with the settled-live-bytes metric Phase 00 validated: v1 is `2.00x` the input at 1, 8, 16 and 31 MiB without exception. v2 is 1,217,519 B at 1 MiB and **1,339,042 B at 1 GiB** - an 850x change in input for a 10% change in memory - with peak RSS flat at 102-104 MB. `memoryBudgetBytes()` (1,099,414 B) is a pure function of configuration and `bufferedBytes()` never exceeds it.
- **A synthetic 1 GiB stream passes the whole pipeline**, all 262,272 frames, against a file that never exists on disk. Peak buffered bytes stayed under budget at every step.
- **Backpressure is structural, not advisory.** Frames are produced only inside `take()`, so a consumer that stops asking stops the encoder and the file reader because nothing else drives them. There is no background pump and **no main-process timer** - the same class of object that kept v1 encoding for a destroyed renderer and surfaced as a shutdown crash.
- **Frames are pulled over IPC, one symbol at a time.** The largest response is one symbol plus 32 header bytes. `select` returns no path, and the metadata that crosses the boundary is asserted to contain neither the temp directory nor any drive-letter path. The renderer is never handed a filesystem primitive; the whole privileged capability is a three-method file handle held in main.
- **The 4 GiB boundary is crossed for real**, not inferred: a session over a file just past 2^32 was driven far enough to prove the sender issues a 64-bit read position no uint32 could express, and every position it passes is a `bigint`.
- **Preflight streams the file once to hash it** at a measured 390-520 MiB/s - under three seconds per gigabyte against a 5,120 B/s optical link - and re-stats afterwards. A file rewritten mid-hash or truncated mid-transfer is caught at the point it happens rather than as a verification failure hours later.
- **Compressibility is sampled from three windows of the actual bytes and deliberately not acted on.** `compressionMode` stays NONE; applying it is Phase 08. Phase 00 established that entropy, not extension, is the real content effect, so Phase 08 inherits a measurement rather than a guess.
- **Repair symbols are produced but not yet decoded.** The symbolizer emits systematic symbols first, then XOR repair over a soliton-selected subset reproducible from `symbolId` and `sourceSymbolCount` alone. Tests assert the XOR identity against the same neighbour function a receiver will call. **The degree distribution, the 0.05 repair overhead ratio, and any recovery guarantee are Phase 03's subject** - this phase claims nothing about how much loss the code survives.
- **The shipping UI still uses v1.** The v2 sender is wired end to end through service, registry, four IPC channels, preload bridge and shutdown teardown, and is driven by tests through the real registration - but `QRCanvas` and `App.tsx` still drive v1. Display cadence is Phase 04 and transfer UX is Phase 09; wiring the renderer now would mean doing it twice. The gate's wording anticipates this: "No whole-file sender allocation remains on the v2 path."
- **No v1 transfer file was modified.** `session-manager.ts`, `container.ts`, `protocol.ts`, `fountain-encoder.ts`, `fountain-decoder.ts` and the renderer are untouched, so every v1 claim below still stands.
- **Suite counts after the phase:** desktop **439 PASS / 31 files** (up from 395 / 28), PWA **71 PASS / 12 files** (unchanged - this phase touches no receiver code). Both typechecks, both production builds, `test:packaged`, doctor (0 warnings) and drift all PASS.
- **Suite runtime rose from ~4 s to ~18 s**, almost entirely from two tests: the 1 GiB stream (8.3 s) and the 4 GiB read-position proof (9.2 s). The second is expensive because reaching a read position above 2^32 requires hashing everything before it. Both are headline gates and were kept for that reason; if the inner loop later matters more, the 4 GiB case reduces to a plan-level assertion at zero cost.
- **Phase 03 (systematic fountain / segmented recovery) is unblocked.** The one number it must justify is `repairOverheadRatio`, currently 0.05 and backed by no recovery evidence at all.

## Large-File / Maximum-Speed Program — Phase 03 (2026-08-20)

**Phase 03 (systematic-first fountain / segmented recovery) is COMPLETE and PASSED.** Gate record: `.ai-team/reports/performance/PHASE-03-SYSTEMATIC-FOUNTAIN-REPORT.md`. Normative FEC profile: `.ai-team/engineering/PROTOCOL-V2.md` §7.2.

- **A loss-free segment costs exactly zero XOR operations.** Not "near-zero" — the test asserts the integer. v1 routes every frame through its equation graph including the systematic ones, which on a clean channel is pure ceremony because the frame already *is* the block. v2 writes a source symbol straight into the segment store and sets its bit; algebra is reached only from `symbolId >= sourceSymbolCount`. Measured over 1 MiB: **v2 decodes at 1,302 MiB/s against v1's 342 MiB/s.**
- **Under 30% loss v2 is 1.5x *slower* than v1** (39 MiB/s against 57). Reported rather than hidden. Two candidate causes were tested — replacing equation `Set`s with swap-removal arrays, and zero-basing the XOR loops — **both measured as no-change and were reverted rather than kept on a plausible theory.** The residual cause is not established; it was not pursued because the margin over the 5,120 B/s optical link is 7,900x.
- **The number Phase 02 left open is settled, and the inherited default was broken.** `repairOverheadRatio` was 0.05 and "backed by no recovery evidence at all". Measured p99 repair ratio needed to close a segment at the default 1 MiB / 512 B profile: **0.00 / 0.46 / 0.71 / 0.71 / 0.72 / 0.94 at 0 / 1 / 5 / 10 / 20 / 30% loss.** 0.05 closes a segment only when nothing is lost. Raised to **0.75**.
- **That default costs clean-channel throughput and the cost is stated.** 0.75 covers every measured rate to 20% at p99 and 30% about half the time, and makes a clean transfer carry 75% more frames — 1 GiB goes from ~33 h to ~58 h at the Phase 00 link rate. It cannot be smaller today because **a segment must close inside the pass in which it is received**: the receiver holds two decoders, so a second display pass restarts an unfinished segment rather than topping it up. The real fix is carrying partial recovery across passes, which needs Phase 06 storage and Phase 07 checkpoints. Phase 04 sets the operating value per transport profile.
- **The requirement is nearly flat from 1% to 20% loss.** It is the tail that costs, not the loss: closing the last few symbols needs a repair symbol touching exactly one of them, which is rare however few remain. There is no cheap operating point above zero — the cost is close to binary.
- **Symbol size is a recovery-efficiency decision, segment size is not.** At a fixed 512-byte symbol, 1/2/4 MiB segments all need 0.92–0.98 at 30%. Holding the segment at 1 MiB and growing the symbol to 2 KiB pushes 30% to **1.55** and 5% from 0.71 to 1.17. Phase 04 must weigh QR capacity and FEC efficiency together.
- **Burst loss costs the same as independent loss** (0.99 against 0.94 at 30% p99). Neighbour selection is pseudorandom over the segment, so index adjacency means nothing to it.
- **Two alternative degree rules were measured through the real encoder and decoder, and rejected.** A geometric degree ladder is 5.8x cheaper at 1% loss (p99 0.08 against 0.46) and better below ~10%, but **failed 40/40 trials at 20% and 30%** under bounded decoder memory, and still needs p99 1.54 against 0.94 when the caps are removed — so the failure is the rule, not merely our caps. Fixed degree 3 is worse everywhere. The robust soliton was the only rule closing every trial at every rate. **FEC profile `0x01` is unchanged and no dependency was added.**
- **Decoder state is bounded per segment and dropped on commit.** At most `maxActiveSegments` (default 2) decoders exist; a completed segment's buffer is *transferred* to the sink and every other structure is dropped in the same call. A later frame for a committed segment costs one bit test. The only file-proportional state is one completion bit per segment — 128 bytes for 1 GiB. Bounds are asserted after every accepted frame, not sampled.
- **Work a hostile stream can buy is capped, and the cheap refusals run first.** Pending equations, neighbour references, tracked repair identities, equation degree, live decoders and declared segment count are all capped. A counting neighbour function proves the ordering: after saturation, 500 further repair frames do not move the call count, so a junk stream cannot buy O(K) of elimination per frame. A manifest declaring more than 2^24 segments is refused at construction rather than allocating a 512 MB bitmap on a phone.
- **The recovery engine is shared with the receiver, not duplicated.** `prng.ts`, `segment-encoder.ts`, `segment-decoder.ts` and `segmented-receiver.ts` are held to the same browser-safety contract as the v2 codec, asserted **inside the mobile-web project**, and a full segmented receive with a third of the frames discarded runs there through the same Vite pipeline the PWA builds with. Phase 05 imports this engine.
- **Neither shipping UI is wired to v2.** The renderer still drives v1 and the PWA still reads v1; display cadence is Phase 04 and receiver wiring is Phase 05. No v1 transfer file was modified, so every v1 claim below still stands.
- **Receiver telemetry exists for Phase 09:** `recovery()` reports per-segment solved, missing, pending equations and `needsMoreRepair`; `stats()` reports accepted, duplicate, rejected, repaired and `xorBytes` as a CPU proxy.
- **Stated deviation:** the plan's optional **adaptive repair ratio was not built.** Adaptation needs either a back channel — the optical link is a screen and a camera, there is none — or partial state across passes, which is Phases 06/07. The measured curve is published as `MEASURED_REPAIR_OVERHEAD` instead.
- **Suite counts after the phase:** desktop **510 PASS / 34 files** (up from 439 / 31), PWA **77 PASS / 12 files** (up from 71 / 12). Both typechecks, both production builds, `test:packaged`, doctor (0 warnings) and drift all PASS.
- **Phase 04 (QR transport profiles) is unblocked.** It inherits the `RepairNeighborFn` seam with three degree rules already measured, the symbol-size/recovery trade-off with numbers on it, and a repair budget that is currently a stated assumption rather than a measured operating point.

## Large-File / Maximum-Speed Program — Phase 04 (2026-08-21)

**Phase 04 (QR optical transport profiles and frame scheduling) is COMPLETE and PASSED, with physical certification explicitly PENDING.** Gate record: `.ai-team/reports/performance/PHASE-04-QR-TRANSPORT-PROFILES-REPORT.md`. Device matrix: `.ai-team/reports/performance/PHASE-04-PHYSICAL-TEST-MATRIX.md`. Protocol change: `.ai-team/engineering/PROTOCOL-V2.md` §4.4.

- **The QR version that maximises throughput is decided almost entirely by one number nobody has measured on a device: camera pixels per module.** Capacity says version 40 carries twelve times what version 10 does; decode says otherwise. Measured at ECC L over 60 independent frames per cell — at **2.5 px/module** version 10 decodes 88% of frames while version 28 manages 7%; at **3 px/module** only version 10 survives at all once Phase 03's repair curve is applied; at **5 px/module** version 24 decodes every frame.
- **Four profiles, separated by what they ask of the camera rather than by capacity.** Reliable (v10, 239 B/frame, 10 FPS, 2.5 px/module, **1,396 verified B/s**); **Balanced — the default** (v18, 686 B, 12 FPS, 4 px/module, **4,795 verified B/s**); Turbo (v24, 1,139 B, 15 FPS, 5 px/module, **17,085 verified B/s**); Experimental (v32, not selectable — its symbol is 765 px across and does not fit a 720-line capture at the density it wants). v1 ships a **nominal** 5,120 B/s that assumes zero loss and carries no repair budget; Balanced's figure is verified and survives the 17% loss measured at its density.
- **Balanced is the default because it is least sensitive to the unmeasured variable.** Turbo falls from 100% to 62% decode between 5 and 4 px/module; Balanced holds 83% at 4 and 98% at 5, so being wrong about the real density costs throughput rather than costing the transfer.
- **ECC was measured and rejected as a lever.** Holding the version fixed and walking L→M→Q→H moved decode success by at most five percentage points, and **H was consistently worse than L**, while costing 58% of the payload at version 20. At low sampling density the decoder cannot resolve the module grid at all, and error correction does not repair a grid that was never read. Every profile is ECC L.
- **The receiver's scan rate is the binding constraint, not the display's refresh.** jsQR over a 1280×720 frame measured 60–93 ms — an 11–17 FPS ceiling — against encode at 6–25 ms. Decode cost is dominated by camera frame size and varies only 1.55× from v10 to v36. An earlier measurement against a version-sized crop showed 5.5× and was an artefact of decoding an image no phone is ever handed.
- **A real render defect on the shipping v1 path is fixed.** `width: 400` across 97 modules is 4.12 device pixels per module: most modules got four, roughly one in eight got five, and every edge fell on a fractional boundary — then CSS resampled the canvas again, and HiDPI a third time. Now an integer module scale, a canvas sized `totalModules × scale`, and an explicit CSS size of `pixelSize ÷ devicePixelRatio`. **Proven both ways**: the same uniformity test passes on the new path and fails on the old one. The QR version is resolved once per transfer and pinned, so the symbol cannot change size mid-stream and force a camera to re-acquire.
- **Frame scheduling is now assertable.** `QrFrameScheduler` pulls rather than pushes, bounds prefetch, honours a minimum frame-hold floor that wins over a faster target, measures cadence instead of restating it, refuses catch-up bursts, and cancels its timer on stop — all against an injected clock, so seventeen timing claims are checked rather than waited for.
- **Manifest byte 43: `reserved` → `transportProfileId`, advisory.** Unknown values are reported, never rejected, because the field cannot affect interpretation — everything decoding needs is already its own field. **Every golden vector generated before the field existed is byte-identical after it** (`manifest-basic.bin` still hashes to `858330198c…`); a new vector pins the new semantics. 22 vectors, reproducible.
- **One place decides transport now.** `configFromProfile` sets symbol size, segment size and repair overhead from a single measured object, so the three numbers that set throughput can no longer drift apart as three defaults. Every profile keeps 2,048 symbols per segment, which is where Phase 03 measured recovery efficiency going flat.
- **Zero wrong decodes** across thousands of degraded captures: jsQR either decoded exactly or returned nothing. Counted separately rather than averaged in, because a silent wrong decode is far worse than a miss.
- **PHYSICAL CERTIFICATION IS PENDING AND NOTHING CLAIMS OTHERWISE.** `physicallyCertified` is `false` for all four profiles and a test asserts it. The matrix specifies the runs, the telemetry schema, the pass criteria, and — written in advance — four findings that would falsify a Phase 04 decision. Two rows of that schema depend on the capture pipeline Phase 05 has not built.
- **Stated deviations:** the FPS targets (10/12/15/20) sit below the plan's 15–60 range because the measured scan ceiling is 11–17 FPS, and they are the weakest numbers in the phase; the plan's benchmark version list (20–40) was the wrong region, so 10/14/18 were added and turned out to matter more; the scheduler is not wired into the shipping UI (Phases 05/09); Turbo cannot auto-fail-back because there is no back channel, so only the "instruct clearly" half of that gate is implemented; compression is deliberately not a profile field because Phase 08 decides it from sampled entropy. Two harness artefacts were found and fixed mid-phase and are recorded because each changed a conclusion.
- **Suite counts after the phase:** desktop **600 PASS / 38 files** (up from 510 / 34), PWA **77 PASS / 12 files** (unchanged — this phase touches no receiver code). Both typechecks, both production builds, `test:packaged`, vector regeneration, doctor (0 warnings) and drift all PASS.
- **Phase 05 (PWA capture and decode workers) is unblocked.** It inherits a profile to build against, the measurement that scan time over a full camera frame is the throughput ceiling, and one field it must plumb through — `symbolSpanPx` from jsQR's corner locations, which turns camera pixels per module from a swept parameter into an observation.

## Large-File / Maximum-Speed Program — Phase 05 (2026-08-21)

**Phase 05 (iOS PWA camera, decode workers, backpressure) is COMPLETE and PASSED.** Gate record: `.ai-team/reports/performance/PHASE-05-PWA-CAPTURE-WORKERS-REPORT.md`. Receiver architecture: `mobile-web/ARCHITECTURE.md`.

- **Everything downstream of the camera now runs off the main thread, and the number that mattered was not the one expected.** The old receiver ran jsQR in a worker and did frame parsing, duplicate detection, fountain elimination, ripple, container parsing and the whole-file SHA-256 on the main thread inside a React callback. Per frame that was only 8–12 µs. **The verification block is what a user felt: one uninterrupted 117 ms stretch at 31 MiB** — a `longtask` by the browser's own definition, at the exact moment the app reports success. Total main-thread work moved: 30 ms at 1 MiB, 97 ms at 4 MiB, 330 ms at 16 MiB, **629 ms at 31 MiB**. Desktop CPU; a phone is several times slower.
- **The queue bound holds under conditions far worse than a phone.** Real `ReceiverClient`, virtual clock, capture faster than decode: 30 Hz/80 ms for 120 s, 60 Hz/90 ms for 120 s, and 60 Hz/300 ms for 300 s. In all three, **peak frames in flight = 2 and peak worker queue = 2**. The worst case attempted 18,000 captures, submitted 1,001, skipped 16,999, and grew nothing. A skipped capture costs one timer — the loop asks `canAccept()` before it reads a single pixel.
- **The bound could not live in the worker, and the first implementation that put it there was unreachable code.** jsQR is synchronous, so a worker is never decoding one frame and receiving another; anything posted early waits in the worker's own message queue, which is unbounded and which the worker cannot inspect. The bound is the client's, resting on one contract: **every posted frame gets exactly one terminal event**, stale and cancelled ones included, because a leaked slot lowers the ceiling permanently and enough of them wedge capture — a queue bound that silently becomes a deadlock.
- **Receiver memory is now a function of the segment, not the file, and it is measured.** Peak decoder bytes over a real v2 transfer: 1,405,185 at 4 MiB, 1,405,186 at 16 MiB, **1,405,190 at 64 MiB**. A 16× change in file size moves it by four bytes. That is Phase 02's sender guarantee held on the receiver.
- **One worker, not two, and the measurement that decided it.** Protocol + CRC + dedupe + FEC is **0.27% of the jsQR decode it follows** (0.11 ms against 41 ms). A second worker would add a hop and a copy to save a quarter of one percent. Stages are separate modules so Phase 06 can split storage out if OPFS writes block.
- **Early dedupe is 6.1× (v2) / 7.3× (v1) faster than the full path — and the first benchmark said the opposite.** The control disabled the fingerprint set by setting its capacity to 1, but a one-entry set still answers an immediately repeated frame from cache, so both arms measured the same fast path and reported a 0.76× "slowdown". **The corrected control changed the number by 8×.** Recorded because a harness artefact that flatters a design decision is the most expensive kind.
- **Five contradicting flags in the receive screen were replaced by one authoritative state machine.** `cameraState`, a protocol snapshot with its own state, `startRequested`, `cameraActive` and `receivingAnnounced` could all disagree, and the pairs that did produced this receiver's two worst shipped bugs. Whether the camera runs, whether cancel means anything, and whether session buffers may still be alive are now *derived* from one state. Backgrounding is a named `INTERRUPTED` state — same privacy posture, session cleared — and every live state returns deterministically to `IDLE`. `EXPORTING` deliberately absorbs backgrounding, because the iOS share sheet hides the page.

## Large-File / Maximum-Speed Program — Phase 06 (2026-08-21)

**Phase 06 (OPFS receiver storage, offset writes, checkpoints, file-backed export) is COMPLETE and PASSED.** Gate record: `.ai-team/reports/performance/PHASE-06-OPFS-STORAGE-REPORT.md`. Receiver architecture: `mobile-web/ARCHITECTURE.md`.

- **The receiver's memory has stopped being a function of the file, and 4 GiB proves it.** Full receives through the store, on real files: 32 MiB → 13.1 MiB peak JS growth, 128 MiB → 88.8 MiB, 1 GiB → 106.7 MiB, **4 GiB → 125.1 MiB**. A 128× change in file size moves peak memory by 9.5× and *retained* memory by nothing — it settles at zero within noise at every size. The store's own resident bytes are **0** throughout, at every size. 4 GiB is 128× the ~32 MB ceiling this program exists to remove and crosses the 32-bit boundary.
- **Verification no longer allocates the file either, and the old path is exactly as bad as feared.** Assemble-then-`crypto.subtle.digest` allocates the file precisely — 15.87 MiB at 16 MiB, 63.78 at 64, 255.94 at 256 — against a flat ~1 MiB for the streaming path. The heap ratio grows without bound: **12× → 49× → 712×**, because only one of the two numbers grows at all. Digests agree at every size.
- **The cost is a hand-written SHA-256 that is 3.5× slower than the platform's, and it is stated rather than hidden.** `crypto.subtle.digest` is one-shot and needs its whole input resident, so a receiver that never holds the file cannot use it. 116 MiB/s against WebCrypto's 409, which is **about 9 seconds of verification per GiB** on a desktop CPU. Against the ~31 hours the same gigabyte takes optically at Turbo's 9,763 verified B/s, that is under 0.01%. Verification yields to the event loop every 16 MiB so a Cancel is still answered during it.
- **Storage is 8,400× faster than the channel it serves.** Write-through with an `fsync` per segment runs at 78–204 MiB/s and read-back-and-hash at 107–116 MiB/s, against Turbo's 9,763 B/s. That is the answer to whether the synchronous-access-handle design was worth its constraints — worker-only, exclusive, one file at a time: it costs nothing observable.
- **Pre-sizing turns "will this fit?" from an estimate into an attempt.** The file is truncated to the full transport size before the first segment arrives, so a device that cannot hold the transfer fails in the second after Receive is pressed rather than forty minutes in. The browser's quota is checked first, with a margin of 15% or 4 MiB, and **is never called free space**: the preflight labels its answer `reported` or `unknown`, and a browser with no estimate API is allowed to proceed because refusing every transfer there would be worse than starting one the write path can already fail cleanly.
- **One boolean became three refusals, because they are three different things to tell a user.** `full` (free space), `invalid` (an offset disagreeing with the manifest — not a storage problem at all), and `failed` (a broken writer, which freeing space will not fix). Reporting a dead writer as a full disk sends someone to delete photos over an unrelated fault.
- **The store re-derives every offset and refuses writes that disagree with the manifest.** Index outside the plan, an offset the plan does not put that segment at, a length that is not the segment's own, a segment already committed. Those offsets happen to be locally derived today; the check exists because this is the last code between camera-originated data and a byte offset in a file.
- **Export never materialises the payload.** No payload byte crosses back from the worker on the v2 path — only a path, validated on receipt and again at the open against the exact shape this receiver writes. `getFile()` on the OPFS handle returns a `File` referencing the entry on disk, and renaming it to the user's filename keeps that reference. Sealing closes the exclusive handle *before* the path is handed over, because the lock would otherwise fail the export on the last step of an hour-long transfer.
- **Working data has five named outcomes, not a hope.** Cancelled/failed/interrupted → deleted. Verified and exported by share → deleted once `navigator.share` resolves. Exported by download → left for the next session's sweep, because a blob URL is read by the browser's downloader on its own schedule. Crashed/abandoned → left deliberately for Phase 07, collected by a sweep bounded twice, by age (24 h) and by count (3).
- **Stated deviations:** no real OPFS was exercised — Node has none, so tests run against a fake modelling a quota, an exclusive lock, a dying writer, a short write and the early Safari revision whose "synchronous" handle returned promises, and benches run against real files through `fs`; the 1 GiB unit test uses a generated backing that stores no bytes, which is the only way to run it and still fails on a misplaced segment because unwritten ranges read back as zeros; **no iOS export size limit is claimed** (Apple publishes none, `showSaveFilePicker` does not exist there) — only that DEQR imposes none; the worker protocol moved **1 → 2**, so a cached shell against a fresh worker bundle now fails at the handshake by design; v1 still assembles in memory and keeps its 64 MiB `LIMITS` ceiling; the shipping desktop sender still emits v1, so the OPFS path has no user-facing flow until Phase 09; resume is not offered (retention defaults to `discard`); `heldBytes` changed meaning to "bytes resident in JavaScript memory", and a `segmented-receiver.ts` doc comment that contradicted its own code about the committed bitmap was corrected with no behaviour change.
- **The benchmark found two defects in its own gate, both of which would have made a passing test meaningless.** `heapUsed` excludes typed-array bytes — a receiver holding an entire gigabyte in one `Uint8Array` would have reported a *flat* heap and passed; every memory reading now uses `heapUsed + arrayBuffers`. And the capability probe, written for the promise-returning Safari revision, caught the harness itself: the bench had opened its file with `a+`, and append mode ignores the position argument, so every computed offset would have collapsed to "the end".
- **Suite counts after the phase:** PWA **206 PASS / 20 files** (up from 159 / 18), desktop **609 PASS / 39 files** (up from 600 / 38). Both typechecks clean; `npm run mobile-web:build` clean, receive worker emitted as its own 198.86 kB hashed chunk. Phase 06 adds 56 tests and updates five existing files with every prior assertion preserved.
- **Phase 07 (integrity and resume) is unblocked.** It inherits `checkpoint.json` — schema version, plan, declared digest, and a committed-segment bitmap sized by segment count rather than progress, written before the first segment lands so an immediate crash still leaves something identifiable; both halves of the retention policy already implemented and tested; `Sha256Stream` on the shared browser-safe path, drivable per segment as easily as per file; and one measurement worth having before designing resume — **verification costs ~9 s/GiB**, so a resume that re-verifies from scratch on every reconnection would spend more time hashing than a fresh transfer spends scanning. **Delivered 2026-08-21 — see the Phase 07 section below.**

## Large-File / Maximum-Speed Program — Phase 07 (2026-08-21)

**Phase 07 (authoritative integrity, durable checkpoints, resumable sessions) is COMPLETE and PASSED.** Gate record: `.ai-team/reports/performance/PHASE-07-INTEGRITY-RESUME-REPORT.md`. Receiver architecture: `mobile-web/ARCHITECTURE.md` §Resume. Protocol decisions: `.ai-team/engineering/PROTOCOL-V2.md` §12.

- **A transfer interrupted at 90% now finishes in 10% of the time, and the thing that decides whether it is real did not move.** 4 GiB interrupted after 1,658 of 1,842 segments, restarted from nothing but the device: **1,658 segments adopted in 5.55 ms** from an **810-byte** checkpoint, 5.45 MiB heap growth, store resident **0 B**, and the result verified against the original digest. At the Balanced profile that turns a 249-hour transfer into a 24.9-hour resume — a **224-hour** saving, all of it optical.
- **Adoption is bounded by the segment count, not the file.** 32 MiB → 5.05 ms, 128 MiB → 3.81 ms, 1 GiB → 6.56 ms, 4 GiB → 11.24 ms. A 128× file is a 2.2× adoption, and the whole difference is JSON. **This is why the receiver attempts a resume on every session** rather than asking the user whether to look: at 11 ms for the largest transfer the program contemplates, looking is free.
- **The one-way channel forced an asymmetric design, and it is the right one.** There is no acknowledgement path, so the receiver resumes *automatically* (it already knows the session, file, digest and plan from the manifest) and the sender is *told* by a **40-character resume token** the user carries — Crockford base32, CRC-guarded, carrying session id, file id, segment count, a 5-byte digest prefix and the lowest segment still needed. Crockford because the string is read off one screen and typed into another: no `I`/`L`/`O`/`U`, and the reader folds the three confusions people actually make. **All 1,240 single-character substitutions of a real token are enumerated in the tests and every one is rejected** — the failure that matters is not a token that fails to decode but one that decodes to a *different valid token*.
- **Restarting at the lowest missing segment is conservative by construction.** The sender re-sends some segments the receiver already holds, each costing one bit test, and skips nothing it needs. The alternative — a compressed set of exactly the missing segments — saves channel time in a rare case and costs a token nobody can read aloud (231 bytes of bitmap at 4 GiB is 370 characters).
- **SHA-256 over the reconstruction is still the only authority, resumed or not.** A resumed transfer is hashed end to end exactly as a fresh one is, at 114–116 MiB/s (8.82 s/GiB, confirming Phase 06's figure). Verification runs **exactly once, at the end**, which is the structural answer to the plan's warning about re-verifying on reconnection. A checkpoint says which bytes were written; it has never been evidence about what they are.
- **Retention became a function of *how* a session ended, and that is a deliberate privacy-posture change.** `cancelled` and `failed` discard; **`interrupted` now retains**, where it previously deleted. The user did not choose to be backgrounded and is likely to come back; the partial file is bounded by the existing sweep (24 h, 3 sessions) inside OPFS, which no other origin can read and the Files app does not show. **A cancel still deletes immediately.** The reason travels on the wire because only the main thread can tell a Cancel tap from a backgrounded tab, and an **unrecognised reason is a refused message, not a defaulted one** — guessing there would mean guessing whether to delete somebody's partial transfer.
- **Six refusals, each its own code, and each clears the directory.** `CHECKPOINT_ABSENT` (ordinary first run), `UNREADABLE`, `SESSION_MISMATCH`, `FILE_MISMATCH`, `PLAN_MISMATCH`, `INCONSISTENT`. Clearing matters as much as refusing: a directory holding another transfer's bytes, left in place and then pre-sized, would read its gaps back as *that data* rather than as zeros. Two further cases — a missing data file and a truncated one — are caught after the checkpoint validates, because a checkpoint cannot speak for the payload.
- **Data the hash rejected is destroyed at once, whatever the policy says.** `HASH_MISMATCH` returns a result with **no `value` field at all**, so no export route exists to ignore the code with, and the working file is deleted — otherwise a later resume would adopt bytes already known to be wrong and fail identically after scanning the whole transfer again.
- **Verification reports its own progress.** A new `verify-progress` event, ~60 per GiB at the hash's existing yield boundaries, epoch-bound so an abandoned session's hash cannot post against the one that replaced it. Nine seconds of silence at the moment a user is watching hardest is what it exists to prevent.
- **Stated deviations:** the token's 5-byte digest prefix is a wrong-file guard and **not** an integrity check (a test asserts explicitly that a digest differing past byte five is not caught, because the limit of a check has to be recorded); **no per-segment digest was added** — it would need a sender-side protocol change and would only catch what the final SHA-256 already covers, recorded as decided-against in `PROTOCOL-V2.md` §12; **a segment interrupted mid-recovery is still restarted**, since persisting its equations means persisting a FEC graph, which the program rules forbid; the retention change above; no real OPFS was exercised (unchanged from Phase 06, still Phase 11's); the worker protocol moved **2 → 3**, so a cached Phase 06 shell fails at the handshake by design; the sender's resume is reachable through `streamTransfer.select(resumeToken?)` but **has no UI** — a screen to type a token into is Phase 09's, per the brief's "expose typed states/events only".
- **A test caught a real defect in the code it was written against.** `readCheckpoint` collapsed "there is no checkpoint" and "there is one and it is broken" into the same `null`, so a corrupt checkpoint reported as `ABSENT` and its payload was left in place instead of cleared. `readCheckpointEntry` now returns both facts.
- **Suite counts after the phase:** PWA **262 PASS / 23 files** (up from 206 / 20), desktop **643 PASS / 41 files** (up from 609 / 39). Both typechecks clean; `npm run mobile-web:build` clean, receive worker chunk 206.55 kB. Phase 07 adds **90 tests** and modifies no prior assertion.
- **Phase 08 (compression and adaptation) is unblocked.** It inherits a verified path that does not care how a transfer got there; a checkpoint already carrying `originalSize` and `transportSize` separately, so a compressed transfer needs no new field — only permission for the two to differ, which `verifyV2` currently refuses; a resume token bound to `segmentCount`, so a token minted under one compression setting is already refused under another by a check that exists; and the remaining half of Phase 03's `0.75` repair overhead — whole segments now survive an interruption, partial symbol recovery within one still does not. **Delivered 2026-08-22 — see the Phase 08 section below.**

## Large-File / Maximum-Speed Program — Phase 08 (2026-08-22)

**Phase 08 (extension-neutral transport, sample-based adaptive compression) is COMPLETE and PASSED.** Gate record: `.ai-team/reports/performance/PHASE-08-COMPRESSION-ADAPTATION-REPORT.md`. Wire format: `.ai-team/engineering/PROTOCOL-V2.md` §4.5. Receiver architecture: `mobile-web/ARCHITECTURE.md` §Compressed transfers.

- **A filename can no longer reach a transport decision, and that is a property of a type signature rather than a promise.** `decideCompression(originalSize, sample, options)` in `src/core/compression-policy.ts` has no parameter that could carry a name, an extension, a MIME type or a path. A test asserts its arity and its source text; a benchmark and an end-to-end test open the *same buffer* five times as `.txt`, `.zip`, `.pdf`, `.xlsx` and `.bin` and assert one decision, one transport size, one segment count and one digest — for compressible and incompressible content alike.
- **A compressible file now takes about a quarter of the optical time.** This repository's own TypeScript, 16 MiB, through the real sender at the Balanced profile: ratio **0.269**, optical hours 0.97 → **0.26**, effective original throughput 4,786 → **17,820 B/s**, a **3.72×** speed-up. Tabular data reaches 8.87× and JSON 11.12×. **Incompressible bytes bypass entirely** — `applied=none`, transport size identical to the original, for the price of one 48 KiB sample.
- **The sample decides whether to *try*; the file decides whether to *use*.** Three bounded 256 KiB windows gate a full sizing walk, and the walk's measured total goes through the same threshold again, so a sample that guesses wrong costs preflight time and never transport correctness. A test builds the adversarial file — text in exactly the three windows the sampler reads, entropy in the 99% between — and asserts it goes out uncompressed. The walk is **fused into the SHA-256 pass the sender already made**, so an exact `transportSize` in the first manifest costs one pass, not two.
- **The transport stream is a container, not a stream.** `[u32BE length][gzip member]` per fixed run of original bytes. Every member is delimited before it is decoded, every window's output length is a manifest-derived constant, and a seek costs one window instead of everything before it. One gzip stream over the file would have failed on all three counts, and would additionally have depended on whatever multi-member behaviour a user's Safari ships.
- **No new dependency.** `node:zlib` on the sender, `DecompressionStream('gzip')` on the receiver — both already in the target runtimes, both offline, no CSP or bundle impact beyond the 9 kB of DEQR code driving them. The plan's WASM audit does not apply because nothing was proposed.
- **Both defaults are measured, not chosen.** zlib **level 6**: 15.7% more off the wire than level 1 for 2.7× CPU that is invisible against an hours-long link, where level 9 buys 0.2% for another 1.5×. **1 MiB window** (`compressionParam = 20`): a 64 KiB window throws away 14% of the compression because windows share no deflate history, and 4 MiB recovers only 0.8% more while doubling the phone's expansion buffer.
- **The threshold is a storage decision, and the sweep says so.** Even a 5% gain saves three optical hours per GiB, so on time alone the threshold should be near zero. It is not, because a compressed transfer holds the container *and* the file at once: peak device usage is `originalSize + transportSize`, which is 1.11–1.27× at real ratios but ~1.95× for a transfer sitting on the line. **10% is the default**, matching the plan's 8–10% ask, and it is a configurable field with a measured table behind it.
- **The receiver reserves both files at session start, not at verification.** `original.part` is created and pre-sized alongside `data.part`, so a device with room for the container but not the file refuses in the second after Receive rather than after an hour of scanning — the same bargain Phase 06 made. Decompression then costs **5–8 s/GiB** at 124–193 MiB/s, and hashing is unchanged at 113–119 MiB/s, agreeing with Phase 06's figure.
- **Integrity semantics did not move.** `sha256` and `originalSize` describe the original file in both modes; verification still hashes what the device holds, read back. What changed is that a malformed container now fails *before* the hash with a code naming the container, where the same corruption would previously have surfaced as `HASH_MISMATCH` minutes later. Five refusals, each its own code, each bounded by the manifest rather than by the stream — including an allocation ceiling checked before any buffer is created and verified tight to within 1% of real zlib output.
- **Stated deviations:** the receiver holds two files (bounded, reserved up front, and the reason the threshold is 10%); `DecompressionStream` is required to receive a compressed transfer (Safari 16.4+, no new floor in practice, refused at the manifest where a user can act on it); the synthetic corpus fixtures compress unrealistically well and the real-source row is the one to quote; a backward seek recompresses from window zero because an index of window lengths would scale with the file; the golden vector `manifest-compressed.bin` moved because byte 42 gained a meaning it never carried on any wire; GZIP mode has a new `originalSize ≤ 2^32 × windowBytes` ceiling (4 PiB at the default window); and **neither shipping UI is wired to any of it** — the metrics are recorded on both sides and displayed by neither, which is Phase 09's.
- **The worker protocol moved 3 → 4.** `verify-progress` names which of the two verification passes it reports, and `progress` carries `originalBytes`, `transportBytes` and `compressionMode` — two sizes, never one. A cached Phase 07 shell against a Phase 08 worker fails at the handshake by design. The desktop IPC boundary gained the same pairing: `StreamingTransferMetadata` now carries `transportSizeBytes` and the applied decision, and `StreamingProgressView` carries `transportBytesTotal`.
- **Suite counts after the phase:** desktop **696 PASS / 45 files** (up from 643 / 41), PWA **282 PASS / 24 files** (up from 262 / 23). Both typechecks clean; `npm run mobile-web:build` clean, receive worker chunk 215.59 kB. Phase 08 adds **73 tests** and changes four pre-existing ones, each accounted for in §10 of the report; no prior assertion was weakened or deleted.

- **The wire format was already hard; the seams were not.** Auditing the v2 parser, the segment decoder, the FEC caps and the GZIP container found nothing to fix in any of them. Every defect this phase found sits at a joint, where one hardened component hands something to another.
- **Every compressed transfer received to OPFS was being discarded by DEQR's own security guard.** The receiver writes two payload files — `data.part` for what the segments carried, `original.part` for the file when those segments carried a container — and the allowlist validating a `verified` message on arrival at the main thread named only the first. A compressed transfer would scan, recover, decompress, pass its SHA-256, and then have the message announcing it silently dropped; `export.ts` would have refused to open it for the same reason. `isReceiverSessionFile` is now the closed set of both, and `checkpoint.json` is still not in it. A too-narrow allowlist is a correctness defect exactly as a too-wide one is a security defect.
- **A manifest-level refusal never reached a screen.** `progress().fault` is the only route from the pipeline to the UI, and `beginV2Session`'s refusals set only a rejected-frame reason — so a phone pointed at a blocked file type, or at a transfer the browser cannot decompress, scanned silently forever while the copy Phase 09 wrote to explain exactly that sat unreachable in `faultCopy`. Every such refusal is now a terminal session fault.
- **`loopback:start` could crash the privileged process from the renderer.** Its options object was read as `any` inside a `setInterval` callback, and a throw in a timer reaches no caller: it surfaces as Electron's main-process error dialog. Renderer arguments are now typed and clamped once at the IPC boundary, and no renderer-supplied structure reaches a timer.
- **A checkpoint on the device was read and decoded unbounded.** `base64ToBytes` allocates three bytes per four characters and the length check ran after the decode. Both the file read and the base64 string are now bounded by `RECEIVER_POLICY.maxCheckpointBytes`, before the allocation they exist to prevent.
- **One policy object, and the test that keeps it one.** `src/core/receiver-policy.ts` holds every receiver-side maximum — frame, filename, segment, symbol, FEC budget, active decoders, queued frames, checkpoint, decompression window, worker pixels. Seven modules read it and `tests/core/security-limits.test.ts` compares it against the constants those modules expose, so reintroducing a literal fails the build. `V2_LIMITS` stays separate and means something different: what the **wire format can express**, which policy may narrow and may never widen — asserted in that direction.
- **A refusal is decided before a device is touched.** `manifestPolicyRefusal` runs after the parser proves a manifest self-consistent and before storage is provisioned. A manifest declaring 2^24 + 1 segments now creates zero bytes on the device and reports `SEGMENT_COUNT_EXCEEDED`; previously it reached `SegmentedReceiver`'s constructor inside the provisioning callback and surfaced as `CHECKPOINT_INCONSISTENT` — a sentence about a checkpoint that had nothing to do with it.
- **Recovery is now fuzzed, not only parsing.** The parser suite already proved no byte string can make it throw. This phase holds the *decoder* to the same standard against attacks made of quantity and identity rather than shape: 50,000 identical repair frames leave `pendingEquations`, `pendingNeighborRefs`, `xorBytes` and `heldBytes` unchanged from after the first; 20,000 distinct ids the algebra cannot consume saturate rather than grow; 10,000 frames at a completed segment add zero XOR bytes; 5,000 header-corrupted frames never once report `sessionComplete`.
- **Nothing on the wire changed.** No edit to `protocol-v2.ts`, `protocol.ts` or `container.ts`; the 24 golden vectors regenerate byte-identically and all 52 vector assertions pass. **The worker protocol stays at 5** — no message shape changed, so a cached Phase 09 shell still handshakes.
- **Stated deviations:** no dedicated fuzzer (none exists in this offline-only project's tooling, so seeded property testing is used instead, and it explores less than a coverage-guided run would); **no benchmark was re-run** — the performance argument is from the shape of the change, one integer comparison placed ahead of an existing O(n) fingerprint, and is labelled an argument rather than a measurement; v1's `LIMITS` are deliberately not folded into the receiver policy, because v1 is a frozen format with a different unit of allocation; and `StreamingSessionRegistry` has no concurrent-session cap, accepted because every session costs a modal file dialog and a human choosing a file.
- **Suite counts after the phase:** desktop **842 PASS / 51 files** (up from 789 / 48), PWA **378 PASS / 28 files** (up from 347 / 27). Both typechecks, both production builds, `test:packaged`, deterministic vector regeneration, doctor (0 warnings) and drift all PASS. Phase 10 adds **84 tests** in four new files and **modifies no existing test**. No prior assertion was weakened.
- **Phase 11 (benchmark and physical certification) is unblocked.** It inherits `worstCaseDecoderBytes`, which states the memory claim as arithmetic a certification run can compare a measured resident set against; a compressed-OPFS export path that is now correct and has still never run against a real OPFS; and two refusals — `UNSUPPORTED_COMPRESSION` and the manifest-policy codes — whose copy is asserted and whose layout no iPhone has yet displayed.

## Large-File / Maximum-Speed Program — Phase 11 (2026-08-23)

**Phase 11 (benchmarking, stress testing and certification) is COMPLETE and PASSED, with the physical gate explicitly open.** Gate record: `.ai-team/reports/performance/PHASE-11-BENCHMARK-CERTIFICATION-REPORT.md`. Physical evidence template: `.ai-team/reports/performance/PHASE-11-PHYSICAL-CERTIFICATION-MATRIX.md`. Machine-readable results: `.ai-team/reports/performance/phase11/`.

- **The pipeline is certified to 4 GiB and the product is certified to nothing.** 35 hash-gated end-to-end transfers, 1 KiB through 1 GiB across compressible, structured and random data, plus 2 GiB and 4 GiB, all verified byte-exact. Every row compares **three independently computed digests** — the fixture generator's, the sender's preflight, and the receiver's hash of what it actually stored — so the sender cannot pass by agreeing with itself. **No physical row was executed**, so per the programme's own rule the certified maximum transfer size is **0 bytes** and no maximum-size or maximum-speed claim may ship.
- **Memory is a function of configuration and not of the file, measured rather than argued.** Receiver held bytes were **1.34 MiB at 10 MiB and 1.34 MiB at 4 GiB**; the sender's declared budget is 1.39 MiB and its observed peak buffer 1.37 MiB, at every size. Peak process heap stayed between 59 and 89 MiB across the whole ladder including the 4 GiB row.
- **Balanced delivers 4,631 verified bytes/sec, and 43% of that link is spent on symbols nobody needed.** The repair budget is emitted unconditionally — there is no back channel to learn the receiver already has a segment — so at zero loss 39–44% of delivered frames are redundant. Removing that would be worth **1.78×**: 1 GiB falls from 64.4 hours to 36.2. Recorded as a finding, deliberately not implemented, because it is a protocol change and this phase's job was to measure.
- **Loss degrades in a cliff, and the cliff has an equation.** Every rate up to Balanced's declared 20% design loss completes in one pass at a 5% throughput cost. 30% completes only after **17 passes at 280 B/s — 17.7× slower**. Above `(1+r)(1−p) ≥ 1.05`, i.e. **p > 0.40** at Balanced, no number of passes can ever complete a transfer: the receiver holds two active segments, so a segment that misses its window loses all partial progress. Proved by the 50%-corruption row, which ran 20 passes and never recovered a single segment.
- **Corruption, duplicates and reordering cost nothing beyond their loss.** 10% corruption produced a 10.08% reject ratio — the CRC refused exactly the damaged frames and admitted none. **No corrupt frame was accepted in any run of this phase.** 25% duplicates were absorbed with identical throughput and memory. A 512-frame reorder window raised held memory to 2.68 MiB, which is two active segments, which is the bound. A hostile mix of all five impairments at once still completed in one pass with a matching digest.
- **A resume costs 6%.** Interrupted at 60% and resumed from a token read off a *fresh* pipeline over the same storage, the whole round trip cost 1.06× one uninterrupted run and skipped 10,944 frames — 15.2 minutes of a 30-minute transfer.
- **The receiver ran against a real OPFS for the first time in the programme.** `scripts/bench/browser/` drives the shipping `ReceivePipeline` and `ReceiverStorage` in a real worker with no injected environment: **10 checks, 10 passed**, including the one Node `fs` structurally cannot test — **the export handoff**, where `seal()` releases the exclusive sync access handle and the main thread opens, streams and re-hashes the sealed file. That is the failure that would have surfaced on a phone at the moment a user pressed save. **Real OPFS is ~100× slower than Node `fs`** (28.8 MiB/s against 2,948), so every storage rate quoted from Phases 06–08 is an upper bound, not a device number. iOS/WebKit remains untested.
- **Storage cannot be the bottleneck.** One write per segment covers 1.34 MiB = 3,584 frames = 298 optical seconds, so even a 200 ms write is 0.07% of the window it serves. All seven backpressure rows verified with held memory flat at 1.34 MiB.
- **Six refusal paths, six clean failures, no digest claimed by any of them.** Empty file, device too small, quota that would be exceeded mid-transfer (**caught up front by the pre-sizing truncate**, which is the design working), device filling up after reservation, a second sender in the room (505 frames counted as foreign, zero rejected, own transfer unaffected), and a cancel that discarded 2.68 MiB in **0.83 ms leaving zero bytes on the device**.
- **Profiles are ranked, not certified.** Fastest completed combination is **Turbo at 5 camera px/module, 10,294 B/s (29.0 h/GiB)**. Broadest stable is **Reliable, which completes at every measured density down to 2.5 px, at 1,178 B/s (252.6 h/GiB)**. **Balanced needs ≥3.5 px/module** and fails at 3. Which profile should be the default therefore depends on a constant nobody has measured, and runs P1/P2 of the physical matrix decide it.
- **Stated deviations:** no real-world file corpus (none legally and locally available; nothing was read from the user's disk, and Phase 08 already proved content reaches transport only through the compression decision); backpressure is half-measured, because a pull-based harness cannot grow a queue — queue-depth backpressure stays Phase 05's measurement; the profile ranking reuses Phase 04's decode surface rather than re-rendering 1.5 million QR symbols per row, and that surface's non-monotonicity (Turbo decodes 76.7% at 3.5 px and 61.7% at 4) shows up in the ranking and is flagged there; `npm run typecheck:phase11` covers this phase's harnesses only, because widening it surfaces pre-existing errors in the Phase 04/05 benches; and two harness defects were found and fixed mid-run (a storage-provisioning window that lost every frame of a sub-segment transfer, and incomplete runs carrying a throughput number into the ranking) — every number reported comes from a run after both fixes.
- **Nothing under `src/`, `mobile-web/src/`, `tests/`, `mobile-web/tests/` or `protocol/` was modified.** A certification that changes the thing it certifies certifies a different product. Suite counts are identical to Phase 10's: desktop **842 PASS / 51 files**, PWA **378 PASS / 28 files**, both typechecks, `typecheck:phase11`, doctor (0 warnings) and drift all PASS.
- **Phase 12 (release gates) is unblocked, and inherits one hard constraint:** it may not ship a maximum-size or maximum-speed claim. The only supportable wording is §12 of the phase report — no 32 MB protocol limit, streaming and multi-gigabyte safe, supported maximum equals whatever passes physical certification, which has not been run.

## Large-File / Maximum-Speed Program — Phase 13 (2026-08-24)

**Phase 13 (physical iOS transfer remediation) is COMPLETE at the code level. Verdict: NOT ACCEPTED — PHYSICAL IOS TRANSFER GATE PENDING.** Reports: `.ai-team/reports/performance/PHASE-13-IOS-PHYSICAL-TRANSFER-REMEDIATION-REPORT.md`, `IOS-PHYSICAL-TRANSFER-ROOT-CAUSE.md`, `IOS-TRANSFER-TELEMETRY.md`, `IOS-TRANSFER-PHYSICAL-MATRIX.md`.

- **Why the phase exists.** A real iPhone test failed: the desktop displayed every scheduled frame and reached its end-of-pass screen while the receiver stayed in `Receiving transfer` with the camera live and delivered nothing. This reopened Phase 12's acceptance and superseded any prior release claim.
- **Four confirmed root causes, all found by reading the shipping code and each proven by a test that fails on the old code.** (1) The sender stopped permanently — `take()` returned `null` once the budgeted repair was spent, so a receiver short by one symbol had no possible source for it. (2) The receiver had no state meaning "the frames stopped": `RECEIVING` could only be left by completion, failure, backgrounding or cancel, and the only stall detector watched the *video element*, which was healthy the whole time. (3) **Repair-only recovery is impossible** — the decoder holds at most `k` pending equations and then rejects everything, so a segment with no source symbols never rebuilds; measured at 1.5x, 2.5x and 4x overhead. (4) A failed export wedged the receiver in `EXPORTING`, which did not accept the event its own failure path dispatched.
- **(3) invalidated the first version of the fix.** The recovery tail originally sent only repair symbols; it would have transmitted forever and completed nothing whenever a burst took a whole segment — exactly what a hand moving in front of a camera produces. The shipped tail is **systematic-first**, replaying a segment's source symbols before generating fresh repair, and batched per segment because the receiver keeps only two decoders alive and round-robin made *negative* progress.
- **Contributing, not causal:** the optical symbol was clipped by the desktop window (fixed separately as `65ced2b`; on a 1125x796 client area 132 px of the transfer view sat below the fold, and a clipped QR does not decode at all), and the action dock let content show through it at 8% with no `backdrop-filter` — its opaque rule was gated behind `prefers-reduced-transparency`, which iOS Safari does not implement.
- **State machine.** `INCOMPLETE` and `RECOVERING` added, plus a `STALLED` event driven by *time since the last unique valid frame* rather than camera liveness. Both new states are deliberately absent from `SESSION_CLEARING_STATES` — that absence is the mechanism that preserves partial state. **Only `VERIFIED` can reach `COMPLETE`**, asserted across every state and transition, which is what structurally stops a sender running out of frames from ever meaning "the file arrived".
- **Targeted resume.** A v2 resume token carries run-length gaps so recovery re-sends only the missing segments, and falls back to the 40-character v1 code when the gaps are a single trailing run — which is what an *interruption* produces, and where v1 already said the same thing in 24 fewer characters.
- **Telemetry.** Refusals are now counted by reason, which is the field that names a failure: mostly `CRC_MISMATCH` is optical, mostly `SESSION_MISMATCH` is a second sender, and no refusals at all alongside no progress means frames are not reaching the decoder. Worker protocol moved **5 -> 6**, so a device holding a cached older shell must be re-installed before any physical run.
- **Suites: desktop 885 PASS / 52 files (was 862), PWA 415 PASS / 28 files (was 385) — +53 tests.** Both typechecks, both production builds, doctor and drift all PASS.
- **No throughput claim is made and none may be.** Nothing in the wire format, FEC or QR profiles changed, so Phase 11's modelled figures stand unaltered. What changed is the ability to measure: `usefulThroughput()` reports verified original bytes per second from bytes actually committed to storage.
- **Every physical gate is PENDING**, all nine size tiers and all twelve provoked behaviours. **The certified maximum transfer size remains 0 bytes.** Phase 11 may be rerun; **Phase 12 may not**, until the physical matrix has been executed at least once against a recorded artifact built from this work.
